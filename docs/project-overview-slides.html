Why this exists

The problem

Jira is the system of record, not the report

Boards show work items. Leaders still need cycle time, velocity, WIP aging, and a forecast — without exporting CSVs or trusting a pie chart of every issue.

Direct Jira in the browser is a non-starter

API tokens must stay server-side. Large issue dumps freeze the UI. Rate limits and lookback windows need a controlled API, not ad-hoc client calls.

What we built instead

A Next.js ops surface in front of an Express analytics API. Optional Percona snapshot + Redis so the dashboard can run even when Jira is slow or the token should not be hammered on every page load.

Points or issue count on closed + active sprints. ISO-week fallback if sprint membership is missing. Throughput by YYYY-Www.

Risk

WIP, blocked, load

In-progress aging buckets, flagged/blocked count, assignee load, and time-in-status for open work.

Plan

Forecast

Remaining open issues ÷ last four weeks of throughput → estimated weeks and date.

Paginated table only. Metrics payload does not ship the full issue array to the browser.

Share

Shared contract

shared/ holds metric math and TypeScript types. Backend copies it on dev/build so UI and API cannot drift on “what velocity means.”

Optional data plane

Redis caches Jira GETs. Percona stores a snapshot after POST /api/v1/sync. Dashboard then reads the database instead of Jira on every request.

JQL updated >= last_issue_updated_at with overlap. ?full=true skips the lookback window. Scheduler on SYNC_INTERVAL_MS.

Webhook

How numbers are defined

MetricDefinition in this product
VelocityStory points (or issue count) completed in recent closed sprints plus the active sprint. Dashed line = rolling average. No sprint field → ISO week.
Cycle timeFirst changelog transition into In Progress → done.
Lead timeCreated → done.
ThroughputIssues completed per ISO week. Forecast uses the last four weeks.
WIP agingOpen in-progress issues only: 0–2d / 3–7d / 8–14d / 14d+.
ForecastOpen issues ÷ recent weekly throughput → estimated weeks and date.

Date filters apply to created date, except when a sprint is selected — then the sprint is the window.

Security and delivery

Security

  • Jira email/token only in server env — never in the client bundle
  • Optional BACKEND_API_TOKEN on metrics and issues
  • SYNC_API_TOKEN required in production for sync and webhooks
  • Zod on query params; secrets excluded from logs

How we run it

  • Local: Next :3000, API published :5001 (container :5000)
  • podman-compose.yml / docker-compose.yml
  • Unit tests for aggregations; API contract tests against a running stack
  • Health: GET /api/v1/health

Main API surface

GET /metrics · GET /issues · POST /sync · POST /webhooks/jira · GET /observability/metrics
